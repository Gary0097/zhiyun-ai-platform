# 上游跟踪与安装版在线更新

本功能随独立 PR 交付。发布经过验收的签名资产之前，不能声称已启用在线升级。当前候选版本锁为 2.2.1。

## 上游升级流程

`upstream-watch.yml` 合并到 master 后每天约北京时间 09:17 检查 QwenPaw 最新正式 Release，也可以手动运行。GitHub 定时任务可能延迟。发现高于稳定锁的版本时创建升级评估 Issue，附精确提交；包括已关闭任务在内去重，不重复催办。已有带版本号的升级任务也会识别。

发现新版不等于完成适配：维护者确认任务为 codex-ready 后，按仓库要求在独立分支同步版本锁、产品决策、版本说明及门禁，验证品牌、原生登录、Hub、真实模型调用和 Windows/Linux 升级。人工审核 PR 并合并。检查工作流不修改稳定锁、不自动合并、不发布上游安装包。

## 用户入口

- Windows：右下角智造云托盘 → **检查软件更新**；也可双击 `update-ai-os.cmd`。确认后自动下载并校验，停止本安装目录内的进程，完整备份，再调用现有安装器覆盖原目录。安装器启动单机服务，更新器复核实际运行时版本。Hub 由管理员按原入口重新启动。
- Windows 只检查：`powershell.exe -NoProfile -File update-ai-os.ps1 -CheckOnly`。
- Linux：`sh update-ai-os.sh check` 检查，`sh update-ai-os.sh download` 下载经过同一签名校验的 Linux ZIP。此版本**没有 Linux 自动覆盖、回退或图形更新入口**；管理员停服备份后按现有 Linux 维护流程部署。不能执行 Windows EXE，也不能把下载成功视作升级完成。
- 原来的安装包不含更新入口，须先覆盖安装一次包含入口和可信公钥的正式安装包。源码 Git 工作目录拒绝执行 Windows 在线安装；按 PR 流程升级。

下载仍可能是完整安装包，不是差分更新。后台完成下载，用户不需要另开网站手动下载。当前运行时、品牌与安装器必须一起发布；不直接运行 `pip install -U qwenpaw` 绕过版本锁。

## 发布者的一次性配置

1. 在发行负责人受控环境生成 Ed25519 密钥。私钥只存入 GitHub 的 **update-release** Environment Secret `AIOS_UPDATE_PRIVATE_KEY`，不写入仓库、日志、Issue 或安装包。根据负责人 2026-09-14 的“自动审批”决定，此环境不等待人工环境审批，只允许 `master` 分支进入，保留工作流内版本、标签、草稿和门禁检查。
2. 将 PEM/SPKI 格式公钥作为字符串加入 `scripts/updates/channel.json` 的 `publicKeys`，通过 PR 审核后合并。缺少公钥或密钥不匹配时拒绝签名/安装，不能用临时测试密钥作为生产密钥。
3. 发布包含该公钥与更新入口的初始安装包。以后更换签名密钥时先用旧密钥签名发布同时信任新旧公钥的过渡版本，用户迁移后再移除旧公钥。

生产公钥的 SHA256(SPKI DER) 指纹为 `4286406f9bbab2e8d8095bb9b9b6c4b477cb5cb06616da940fe234b3bdbb5796`。生产私钥在内存生成，经标准输入上传到上述 Secret，本地只保存公钥；GitHub Secret 无法回读私钥，丢失或删除后须走密钥轮换流程，不能用新生成的密钥直接覆盖已部署信任根。

公钥 PR 合并后，从 `master` 运行 **Verify production update signing key** 可验证 GitHub Secret 与客户端公钥一致；该工作流只做内存签名自检，输出公开指纹，不生成或发布安装资产。它不能代替真实签名更新包与跨版本升级验收。

客户端只接受本仓库正式 Release、精确资产路径及 Ed25519 签名的清单，流式检查 SHA256 和长度。HTTPS/GitHub 是分发基础，签名公钥是安装信任根。没有 Release、缺少密钥、下载失败、签名错误和版本不匹配均明确失败，不降级到未校验安装。

## 每次发布

1. 合并并验收目标版本；为 master 上的目标提交创建 `vX.Y.Z` 标签。版本与运行时锁一致。
2. 用现有打包脚本从该标签构建 Windows 离线 EXE 和 Linux 在线 ZIP，验证安装包内版本与源提交，执行 Windows/Linux 实机安装、升级、回退和真实业务路径验收。打包和业务验收目前由发行人员运行，不由监控工作流冒充。
3. 创建同标签的 **draft** GitHub Release，上传 `zhiyun-ai-os-vX.Y.Z-setup.exe` 和 `zhiyun-ai-os-vX.Y.Z-online-installer.zip`。运行 **Sign reviewed update assets**，输入该标签。
4. 工作流要求标签已合并到 master、版本锁一致、草稿非预发布，运行代码门禁，再在受保护环境生成 `aios-update.json` 与二进制 `aios-update.sig`，附到草稿。签名脚本不证明资产构建来源，发行审批人仍须核验资产对应已验收提交。资产一旦签名不得替换；需要重签时重新审核草稿。
5. 人工确认并发布，设为 Latest，客户端才能发现。工作流不会自动发布。对有数据迁移的版本，先确认回退兼容性和数据恢复方法，再允许发布。

## 备份与恢复

更新器使用互斥锁避免并发。停止本安装目录中的运行进程后，若 8088/8000 仍在监听则拒绝修改；不按模糊进程名称停止其他安装。更新期间请勿另行启动服务。含目录链接或缺失安装文件清单时拒绝自动备份。使用停止进程的方式可能中断任务，用户必须先保存工作。

完整备份位于 `<安装目录>/.aios-updates/transaction-<编号>/backup`，包含 Workspace、密钥和 Hub 数据；备份目录权限仅授予当前 Windows 用户和 SYSTEM。缓存和旧备份不重复复制。磁盘不足或备份失败时不安装。备份不自动清理，验收成功后由管理员按保留策略管理。

安装器在解压前将完整文件写入意图持久化到 transaction 内的 `write-intents.txt`，在运行环境安装前记录允许修改的 venv/cache 目录。即使解压中途失败、运行环境安装失败或安装器未能提交卸载清单，恢复也能依据这些记录及升级前快照识别残留文件。

安装失败时保留错误与备份，不自动覆盖数据库。停止单机、托盘和 Hub 后，用 PowerShell 运行该 transaction 目录内独立的 `restore.ps1`。它与更新器共用互斥锁，拒绝并发更新或恢复；该入口保存在备份中，当前安装脚本损坏也能使用。

恢复前统一路径分隔符和大小写，将旧程序以及写入意图涉及的原有文件从备份恢复；如果新版包覆盖了原有未登记文件，也保留并恢复其旧内容。新增程序和失败安装的 Python 包移入 transaction 的 `quarantine`，不永久删除；受管运行目录中升级后新增的未登记文件也会保存在这里，可供人工取回。工作区、密钥、Hub 配置及不涉及安装写入的未知文件保持原样。

如果新版运行时已做数据库迁移，仅恢复程序可能不兼容。先额外保存失败后的数据，再由管理员按该版本的迁移恢复说明，从 `backup` 整体恢复对应工作区及密钥。不要只替换数据库而遗漏 secrets，不自动覆盖用户升级后新增内容。注册表显示版本可能仍是新版，可用旧安装器覆盖修复系统集成。

## 本 PR 验证与边界

- 签名/摘要/长度、错误响应、版本判断、上游去重的自动测试；Windows 真正文件备份与程序回退、Workspace/密钥/配置/未知文件保护、路径穿越拒绝；托盘启动器编译及自检。
- 独立干净工作目录运行 `ZY_ALLOW_NO_CONSOLE=1 node scripts/verify-release.mjs`。该模式检查代码和品牌补丁回归，明确跳过真实运行时控制台检查；不是实机业务验收。
- 已建立生产密钥 Secret 和仅 master 准入的自动签名环境；公钥纳入安装包前必须完成该 PR 的审核合并。尚需运行云端密钥匹配验证、初始安装包发布及真实签名跨版本升级验收。未实施生产更新、未自动合并、未变更当前用户数据。
