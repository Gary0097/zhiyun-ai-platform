# 企业 AI 平台自动化仿真与真实数据双态运行体系

> 本文档把「造一批演示数据」升级为「长期可持续运行的 **Demo / Production 双态验证体系**」。
> 它是后续 6 个 Epic 的权威需求来源，也是交接给最强 GPT 的核心规格。
> 关联文档：`docs/product/DEMO-PRODUCTION-EPICS.md`（Epic 计划台账）、`docs/product/REQUIREMENT-CHANGES-2026-08-24.md`（需求变更）、`docs/handoff/HANDOFF_GPT_2026-08-24.md`（交接）。

---

## 0. 文档目的与定位

- 目标不是单纯把页面填满示例数据，而是让**所有应用、智能体、权限、Token、聊天、用户行为**都能在同一套规则下持续生成，并随时切换时间范围、切换演示/正式数据源。
- 本体系完成后，**后续新开发的 Order Studio、Data Studio、财务、销售、客服等应用可直接复用同一套企业运行数据**，不必各自造数据。
- 本文档记录需求、命名决策、数据流与隔离原则、6 大 Epic、与现有实现的复用与缺口。**不在此实现代码**，实现按 Epic 计划推进。

---

## 1. 总体目标（一段式验收）

> 从一个全新数据库开始，只需执行一次初始化命令，即可自动生成一套从 **2025-12-01 至当前日期**持续运行的企业 AI 环境；任意日期均可查看用户、智能体、聊天、Token、应用、权限、文件及执行统计，并能在**演示环境与真实业务环境之间一键切换**，且所有统计均可追溯到对应底层业务记录。

### 平台应具备的能力

- 自动创建智能体、自动绑定技能、自动分配模型与应用权限。
- 本地模型能够自动生成并执行企业业务数据。
- 从 2025-12-01 到当前日期持续生成完整历史数据，后续每天继续增长。
- 任意选择时间范围（昨天、近 7 天、某月、某季度、自定义日期），立即加载对应数据。
- 支持「演示数据 / 正式数据」一键切换，但产品前台**不出现**「模拟 / Mock / 测试」等影响展示效果的标记。
- 所有统计口径必须互相对应：Dashboard 有调用量则聊天记录中必须有；Token 很高则必须有智能体执行记录。
- 接入真实业务数据后，用真实数据反向校准数据分布、字段结构、使用频次与业务规律。

## 3. 统一数据流（DataContext）

所有查询必须经过统一 DataContext，绝对不要让每个页面自行判断使用哪套数据：

```text
User
 ↓
App
 ↓
DataContext
 ↓
Demo Dataset / Production Dataset
 ↓
Database
```

- DataContext 决定：`data_mode`、`tenant_id`、`environment_id`、`data_source`、`time_range`。
- 页面只消费 DataContext 提供的数据视图，不直接拼接底层表。

---

## 4. 双态隔离原则

- Demo 与 Production **不能共表后随便加字段混用**，至少逻辑隔离，优先物理隔离。
- 所有记录携带：`tenant_id`、`environment_id`、`data_source`。
- **正式模式严禁读取演示记录**；导入真实数据时不污染 Demo 历史。
- 与现有单租户隔离策略关系：企业维度隔离发生在「实例边界」（一套运行实例 = 一个企业，`data_mode` 在实例内再分演示/正式数据集）。

## 5. 详细需求（19 项）

### 5.1 自动创建企业环境（Enterprise Seeder）

一键执行自动创建：

> 企业组织 → 部门 → 企业用户 → 用户角色 → 权限 → 智能体 → 技能 → 应用 → 数据源 → 会话 → 任务执行记录 → Token 统计 → 操作日志。

示例部门：销售部、财务部、采购部、客服部、运营部、管理层。
示例数字员工：销售报价、客户跟进、邮件营销、采购对账、财务票据、售后客服、经营分析。
约束：智能体不能只是数据库一条记录，必须真正关联：

> Agent → Skill → Model → Tool → App → User → Permission → Execution Log。

### 5.2 智能体自动配置（Agent Factory）

按岗位模板自动生成完整智能体配置：

- Agent 名称、岗位、所属部门
- System Prompt、模型、Skill、Tool、知识库
- 数据权限、应用权限
- 最大 Token、执行频率、工作时间、自动任务、人工触发任务
- 成功率、平均响应时间

示例：创建「海外邮件营销数字员工」，自动配置企业联系人搜索 Skill、邮件内容生成 Skill、产品素材生成 Skill、邮件发送 Skill、邮件状态追踪 Skill，并真正调用本地模型执行，而非只写静态记录。

### 5.3 本地模型自动跑业务（Simulation Runtime / Business Activity Generator）

核心链路，不是随机插数：

> 业务事件 → Agent 执行 → Skill 调用 → Tool 调用 → 产生结果 → 形成日志 → 产生 Token → 产生用户行为 → 进入统计。

示例某天：销售人员登录 → 打开报价应用 → 与报价 Agent 对话 6 轮 → 上传 Excel → Agent 调用报价 Skill → 模型执行 → 生成报价文件 → 下载 Excel → 产生 18,420 Token → Agent 调用 +1 → 活跃用户 +1 → 文件生成 +1。

### 5.4 历史数据时间引擎（Time Machine / Time Simulation Engine）

- 默认范围：2025-12-01 ～ 当前日期，每天自动补充当天数据。
- 支持：今天、昨天、近 7 天、近 30 天、本月、上月、本季度、今年、自定义日期。
- 切时间范围时，所有 Dashboard、Agent、Token、用户、聊天、任务、应用数据**同步切换**，不只是图表变日期。

### 5.5 数据必须体现业务周期（不能纯随机）

- **工作日**：周一至周五调用量高，周末明显下降。
- **工作时间**：09:00-12:00、14:00-18:00 调用集中；凌晨仅偶尔自动任务。
- **月度规律**：月初经营分析、财务报表增加；月末财务、采购、销售汇总增加。
- **企业增长**：2025-12 约 6 Agent / 18 用户，到 2026-08 约 22 Agent / 65 用户；不能每天完全一样。

### 5.6 智能体统计必须闭环

至少覆盖：Agent 总数 / 启用 / 停用 / 调用次数 / 成功 / 失败 / 成功率 / 平均响应时间 / 平均任务耗时 / Skill 调用 / Tool 调用 / 活跃 Agent / Top Agent / 使用趋势 / 部门分布 / 用户分布。
例如某个 Agent 显示 2,431 次执行，则数据库必须能追溯到对应 execution records，而非只有仪表盘数字。

### 5.7 Token 消耗体系（含 Token Cost Engine）

- 字段：Input / Output / Total / Cached（如支持）/ Reasoning（模型支持时）。
- 维度：按 Agent、用户、部门、模型、应用、日期。
- 示例：销售报价 Agent 3 月输入 1.23M / 输出 410K / 总 1.64M；Token 必须由真实生成的 conversation / execution 汇总。
- **Token Cost Engine**：即使本地模型无真实成本，也可按模型配置「计费单价」，使 Dashboard 展示成本趋势。

### 5.8 聊天数据

- 由本地模型自动生成真实业务聊天，而非「你好 / 您好有什么可以帮助您」。
- 示例话术：「帮我整理一下沙特这个客户的设备需求」「上次报价是不是含运费」「把报价数量改成 12 台」「帮我重新生成 Excel」。
- 形成：Conversation → Message → Agent execution → Skill → Token。
- 需模拟：多轮、重新生成、文件上传/下载、任务失败、重新执行、人工确认。

### 5.9 企业用户与权限（IAM）

- 角色：超级管理员、企业管理员、部门管理员、普通员工、只读用户。
- 用户属性：部门、岗位、角色、可访问 Agent、可访问 App、可访问数据范围、登录记录、操作日志。
- 示例：销售人员不能查看财务 Agent 的付款数据；财务人员不能修改系统管理员配置。

### 5.10 用户登录行为

- 模拟：正常登录、退出、Token 过期、重新登录、多设备登录、失败登录、长时间未登录。
- 可形成 DAU / WAU / MAU / 登录频率 / 活跃率 / 留存率。
- 示例 2026-08-24：58 企业用户 / 41 人登录 / 36 人使用 Agent / 24 人下载文件。

### 5.11 Excel / CSV 成为平台统一能力（Data Import / Export SDK）

- 所有业务 App 原则上支持 Import（.xlsx / .xls / .csv）与 Export（.xlsx / .csv）。
- 统一支持：字段映射、预览、格式校验、错误行提示、重复数据检查、增量导入、覆盖导入。
- 设计公共 **Data Import / Export SDK**，所有 Studio / App 直接调用。
- 参考真实数据源见 §7。

### 5.12 演示 / 正式一键切换（数据环境）

- 产品上不叫「模拟数据」，叫 **数据环境**（演示环境 / 生产环境，或 Demo / Live）。
- 底层统一 `data_mode = demo | production`。
- 所有查询走统一 DataContext（见 §3），页面不自行判断。

### 5.13 两套数据彻底隔离

见 §4。Demo 与 Production 逻辑/物理隔离，记录带 `tenant_id / environment_id / data_source`，正式模式严禁读演示记录。

### 5.14 真实数据校准（Real Data Profiler）

- 自动分析：字段、数据量、日期分布、部门分布、用户数量、订单数量、金额区间、业务频率、异常比例、聊天语言、Token 分布。
- 让 Simulation Engine 按真实数据特征重新调整，例如真实销售部日均 180 次 Agent 调用，则校准历史曲线。

### 5.15 数据一致性检查器（Data Integrity）

每日自动检查并生成 `Data Integrity Report`，可安全修复的问题自动修复：

- **用户**：登录用户 ≤ 企业用户；Agent 用户 ≤ 登录用户。
- **Agent**：成功 + 失败 = 执行总数。
- **Token**：Agent Token 汇总 = 应用 Token = 企业 Token。
- **聊天**：消息对应 Conversation；Conversation 对应 User；Agent Message 对应 Agent。
- **文件**：下载记录必须存在对应文件。
- **权限**：用户不能访问无权限 Agent。

### 5.16 避免「看起来像假数据」

产品验收要求：不得出现明显生成痕迹，例如所有用户注册日期相同、所有用户每天登录、所有 Agent 成功率 100%、Token 每天完全递增、所有聊天都是 3 轮、所有金额都是整数、所有执行时间相同、周末与工作日流量一样、每个月数据相同。
应允许：失败、波动、异常、休眠用户、低频 Agent、突然增长、业务峰值。

### 5.17 一键企业运行

管理员点击「运行企业数据」，选择：

> 企业模板（制造企业）、起始日期（2025-12-01）、结束日期（2026-08-24）、规模（50 人）、部门（6）、Agent（18）、业务活跃度（中等）、参考真实数据、模型（本地 Qwen）。

点击「生成并运行」后自动完成：企业 → 用户 → 权限 → Agent → Skill → App → 聊天 → 任务 → Token → 文件 → 登录 → Dashboard。

## 6. 拆除与改造点（与现有实现的冲突）

### 6.1 前端「模拟」标记

现有 `plugins/zhiyun-data-core` UI 有「生成 20 条模拟订单 / 生产数据」按钮及「模拟」徽标。按 §2 命名规范，这些属于**后续改造点**（改为「环境 / Demo / Live」措辞），**本轮不在代码层面大改**，先记录。

### 6.2 进度台账分离

现有 `plugins/zhiyun-app-discovery/feature_progress.json` 校验唯一 ID（当前 1-31）且要求 status/progress 配比正确。6 个 Epic 属**新体系**，不宜塞进 31 项台账，改用独立台账 `docs/product/DEMO-PRODUCTION-EPICS.md`。只有当 Epic 拆成可交付能力并达到完成标准时，才考虑在 31 项台账中追加能力条目并同步校验脚本。

### 6.3 单租户实例边界

现有登录/权限（`zhiyun-auth`）已实现「登录门 + 默认账号 + 前端 RBAC 展示」。双态体系在**实例边界**（一套运行实例 = 一个企业）之上，再细分演示/正式数据集；服务端强制鉴权与路由仍需接入。

## 9. 最终验收标准（分解）

1. 全新数据库执行一次初始化命令即可生成 2025-12-01 至当前日期的完整企业 AI 环境。
2. 任意日期可查看：用户、智能体、聊天、Token、应用、权限、文件、执行统计。
3. 可在演示环境与真实业务环境一键切换，demo 数据与 production 数据隔离互不污染。
4. 所有统计可追溯到底层记录：调用量 ↔ 会话，Token ↔ 执行，文件 ↔ 下载记录，权限 ↔ 用户可访问范围。
5. 前台无「模拟 / Mock / 测试」标记（按 §2 命名规范）。
6. 数据具备业务周期与随机波动，不留明显生成痕迹（§5.16）。

## 10. 落地顺序建议

1. **先规格后代码**：本文档 + Epic 台账为唯一权威需求来源。
2. 按依赖推进：Epic 1（Seeder）→ Epic 2（Agent Factory）→ Epic 3（Simulation Runtime）→ Epic 4（Time Machine）→ Epic 5（Data Platform）→ Epic 6（Data Integrity）。
3. 每个 Epic 达到「能力可使用 + 证据留存 + 口径闭环」后，才在台账标记进展；验收以真实浏览器/接口证据为准，不以「存在代码」为准。
4. 开发完成后，回填 `docs/qa` 测试用例与结果、`docs/handoff` 交接文档。
